# Decision Log

Technical decisions made during NEIIST Website development. Each entry records
the decision, alternatives considered, and rationale.

| Date | Decision | Alternatives | Rationale | Author |
|------|----------|-------------|-----------|--------|
| 2026-07-24 | Use Vitest for testing | Jest | Vitest is faster, ESM-native, better Next.js support | AI + tomasmbrito |
| 2026-07-24 | Keep raw pg (no ORM) | Drizzle, Prisma | Existing codebase uses raw pg extensively; migration risk too high for now | tomasmbrito |
| 2026-08-11 | Yarn is the authoritative package manager; delete `package-lock.json` | Migrate to pnpm (matching upstream), keep both lockfiles | All `package.json` scripts and the husky hooks already assume yarn. Two committed lockfiles can disagree and produce different dependency trees for different developers. pnpm is deliberately deferred, not rejected — it is a breaking change to scripts, CI and the server deploy scripts, and should be its own project. | tomasmbrito |
| 2026-08-11 | Deliver via branch + PR on the fork; human reviews and merges | Full autonomy including self-merge | The code handles real card payments and student PII. For security and payment changes a wrong fix is worse than a slow one, so a human reads the diff before it lands. | tomasmbrito |
| 2026-08-12 | **Identity model is `istid`.** Delete `src/lib/db/repositories/*` and `docker/migrations/001_user_uuid.sql`; adopt the upstream `src/utils/db/*` split instead of reviving the fork's own (#82) | Commit to UUID and mount the migration; keep both halves indefinitely | `neiist-dev` kept `istid VARCHAR(10) PRIMARY KEY`, has since built a whole voting system on `istid` foreign keys, and already shipped the dbUtils split this fork was attempting (28 `istid` / 0 `uuid` references in a query layer that runs in production). The fork's half was 1,025 lines with **zero call sites** that had never executed, targeting a migration `docker-compose.yml` never applied. Choosing UUID would have meant rewriting the existing 60+ SQL functions *and* everything upstream has added since, and diverging permanently on schema — the one thing that makes future syncs impossible rather than merely tedious. External users get a synthetic `istid` in the existing column rather than a UUID primary key. | AI + tomasmbrito |
| 2026-08-12 | Stay on yarn until the upstream sync (#90) completes, then revisit pnpm (#112) | Migrate to pnpm now, matching upstream | The lockfile is the least valuable thing to take from upstream; the valuable parts (security bumps, the dbUtils split, voting) need no pnpm. Changing package manager mid-sync adds an install-layer variable to a merge already touching 145 files, and the deploy scripts are the risky surface. commitlint and release-please are separable from that commit and cheap to adopt alone. | AI + tomasmbrito |
| 2026-08-12 | Sync from `neiist-dev` by cherry-picking per theme in waves, never by merging | `git merge upstream/main`; rebase the fork onto upstream | A merge produces 42 conflicted files simultaneously, most of them API routes carrying the #96–#106 security fixes — the failure mode is a security fix silently reverted. Their version is also not automatically better: their Notion webhook fails open when `VERIFICATION_TOKEN` is unset, which #96 already fixed here. Per-file adoption is the only way to keep what the fork does better. See `upstream-sync-plan.md`. | AI + tomasmbrito |
| 2026-08-12 | **Build a migration runner rather than applying DDL by hand.** `scripts/migrate.mts` + `docker/migrations/` + `neiist.schema_migrations`, wired into both deploy scripts (#148) | A documented manual `psql` procedure; adopting a migration tool (Flyway, node-pg-migrate, Drizzle Kit) | The order-integrity plan asked "who applies DDL to production?" and the answer was *nobody, ever* — no `psql` step existed in either deploy script, in this fork or upstream, across 53 edits to `schema.sql`. A manual procedure would have kept the schema dependent on someone remembering; Tomás explicitly asked not to do it by hand. A dependency was rejected because the requirement is small (ordered SQL files, a ledger, a lock) and the repo's constraints are unusual — plpgsql dollar-quoting means the runner must *not* split on `;`, and blue/green deploys mean it must hold a lock. ~250 lines of `pg`, which is already a dependency, beats a tool whose defaults fight both constraints. | AI + tomasmbrito |
| 2026-08-12 | **Every migration must be idempotent**, and `docker/schema.sql` must be edited alongside it | Ordinary forward-only migrations that assume a known starting state; generating `schema.sql` from the migrations | Production's schema is unmeasured and unreconstructable (§1 of `database-migrations.md`), so a migration cannot assume what it is starting from. Idempotence is what makes the runner safe to point at it anyway. Keeping `schema.sql` as the hand-maintained end state means fresh environments never replay history — at the cost of writing the change twice, which is the deliberate trade. | AI + tomasmbrito |
| 2026-08-12 | **Tests run against a real Postgres, not mocks** (#52) | Mock `pg`; use `pg-mem` | The first tests cover `withTransaction`, whose entire contract *is* Postgres behaviour — that `COMMIT` on an aborted transaction returns the tag `ROLLBACK` and raises nothing, that a pooled connection is a different transaction. A mock would assert only that we still believe what we already believed, and the aborted-`COMMIT` bug is precisely a case where the belief was wrong. CI gets a service container; the job is kept separate from `quality` so the build keeps proving it needs no database (#106/#109). | AI + tomasmbrito |
| 2026-08-12 | **`/shop` keeps `force-dynamic`; the other three pages drop it** (#111) | Remove all four, now that the dynamic signal propagates; keep all four | Measured, not argued: with all four removed the build fails on `/shop` with no database reachable, reintroducing the build-time database dependency #106/#109 removed. `/shop` is the only one of the four that never touches the session, so its only dynamism is a database read — which Next does not treat as a signal. The other three call `serverCheckRoles`/`requireRoles` first, and that `cookies()` read is now itself the signal. | AI + tomasmbrito |
| 2026-08-19 | **`pending` means *pending payment*; the SQL transition matrix rejects `pending → ready` and `pending → delivered`** (#78) | A permissive matrix allowing managers to skip straight to delivered | Tomás: "when someone completes a payment via sumup (online) it waits for the payment to be completed and then marks it as paid automatically, but when someone chooses the option to pay in person, then the system has to wait for us to manually mark it as paid, so it's pending payment." Skipping `paid` would leave a delivered order with `paid_at IS NULL` and no record of who took the money. The consequence is that bulk "Marcar como Pago" becomes load-bearing — and it had never worked (#154), so that had to be fixed first, in the PR before this one. | AI + tomasmbrito |
| 2026-08-19 | **`cancelled` is terminal** (#78) | Add `reactivate_order` that re-decrements stock under the same locks | Tomás confirmed nobody un-cancels orders today, and the UI never offered it (`cancelled.allowedTransitions` is `[]`). Leaving `cancelled` mints inventory: the restock trigger has already returned the stock and there is no compensating re-decrement. A manager who cancels the wrong order re-creates it and the order number changes — acceptable against handing out units nobody bought. | AI + tomasmbrito |
| 2026-08-19 | **A payment reference is required only for the SumUp-backed methods** (`card`, `sumup`, `sumup-tpa`), not "everything except cash" (#154) | Keep `payment_method !== 'cash'`; require a reference always and have managers type a placeholder | The old rule rejected `in-person`, `mbway` and `transfer` — every manually-confirmed method, i.e. exactly the flow the endpoint exists for. Those payments have no external reference to record. Decided in SQL (`payment_method_requires_reference`) so the API, the POS and the bulk path inherit one rule instead of three copies. | AI + tomasmbrito |
| 2026-08-19 | **The per-user cap is a wrapper (`new_order_capped`), not an edit to `new_order`** (#100) | Add the cap inside `new_order`; add a `categories.max_quantity_per_user` column | `new_order` is ~280 lines of stock locking, discount redemption and totals. Copying it into a migration to add ten lines creates a second copy destined to drift from `schema.sql` — the exact failure the repository already lived through with the dead repository layer. A wrapper takes the advisory lock, delegates, then validates; a plpgsql `RAISE` aborts the caller's transaction so everything rolls back together. A column was rejected because it duplicates `orderKind.ts` policy into data and needs a management UI. | AI + tomasmbrito |
| 2026-08-19 | **`setOrderState`'s `expectedStatus` is a required parameter** (#78) | Optional with a default, to avoid touching call sites | Every caller has already read the order, so it can always state what its decision was based on. Optional would let a call site silently keep the unguarded behaviour, which is the bug. In a repository with almost no tests, `tsc` refusing to compile is the regression guard — it found all three call sites immediately. | AI + tomasmbrito |
| 2026-08-19 | **Concurrency tests hold a transaction open; `Promise.all` is not accepted as a concurrency test** | `Promise.all` of two calls, which is shorter and reads well | Measured: a `Promise.all` version passed against a deliberately broken `finalize_paid_order` with neither the row lock nor the conditional write. Two pool queries start ~1 ms apart and the unguarded window is microseconds wide, so they never overlap. Holding a transaction open makes the interleaving real and the test fails against the broken version. Every concurrency guard added since is checked by mutation before being trusted. | AI + tomasmbrito |
| 2026-08-20 | **Authorization is expressed as named permissions, not role arrays** (#156). `PERMISSION_ROLES` is the source of truth; `ROLE_PERMISSIONS` is derived | Keep the ~50 inline `UserRole[]` arrays; introduce a role hierarchy where admin implies the rest | Nothing could answer "what can a coordinator do?" without a grep, and the same rule appeared written two ways — the shape that produced #97 and #117. A hierarchy was rejected explicitly: `hasRequiredRole` is an intersection test and always has been, so making admin a superuser would silently grant it every permission it does not hold today — a behaviour change wearing a refactor's clothes. The equivalence test transcribes the pre-refactor arrays and asserts `can()` agrees with `hasRequiredRole` for every permission × role, so a policy change must be written twice, on purpose, and shows up in a diff. | AI + tomasmbrito |
| 2026-08-20 | **`sameSite: "lax"` on the session cookie, not `"strict"`** (#94) | `strict`, as the issue's first suggestion | `strict` is not sent on a top-level cross-site navigation, so arriving from an external link or the OAuth provider's redirect back renders logged-out until the user navigates internally. A real Fenix round-trip cannot be exercised locally, so the reversible choice wins. The cross-site request guard in `proxy.ts` is the layer to tighten if `lax` proves too loose, not the cookie. | AI + tomasmbrito |
| 2026-08-20 | **Uploads are re-encoded through sharp rather than stored as received** (#95) | Validate magic bytes only (the status quo); add a pixel check without re-encoding | One change buys three properties: `limitInputPixels` refuses a decompression bomb at upload rather than inside the image optimizer on a page render; anything appended after the image data does not survive; and EXIF is dropped, which matters because product photos are taken on members' phones and were carrying GPS into a public directory. | AI + tomasmbrito |
| 2026-08-20 | **The last admin-granting role cannot be removed or demoted, enforced in SQL** (#158) | Enforce it in the API route; leave it to operator care | Demonstrated in a rolled-back transaction that removing every `access='admin'` role leaves zero admins, and since role management requires admin or coordinator, recovery needs a `psql` session against production — which per #152 has no documented path. Enforced in SQL because the API is not the only caller and a future one should not have to remember, the same reasoning as #146. | AI + tomasmbrito |
| 2026-08-21 | **Keep `xlsx` on the SheetJS CDN tarball; do NOT move it to the npm registry** (#41) | Migrate to `xlsx` from npm, as the issue proposed, to bring it inside normal audit tooling | Measured: npm's latest `xlsx` is **0.18.5**, the version SheetJS abandoned when they left the registry. The CDN carries **0.20.3**. Moving to npm would *introduce* the two CVEs that 0.18.5 has and 0.20.3 fixes — prototype pollution (fixed 0.19.3) and ReDoS (fixed 0.20.2). The stated benefit is also smaller than assumed: `yarn.lock` pins the tarball with a SHA-1 (`#992725af…`), so a changed artefact fails the lockfile check. Revisit only if SheetJS returns to the registry. | AI + tomasmbrito |
| 2026-08-21 | **Delete ESLint's `max-len`; wire in `eslint-config-prettier`** (#41) | Keep both and keep tuning `max-len`'s ignore list | They expressed the same limit twice — `max-len: 100` and prettier's `printWidth: 100` — but only the formatter can wrap a line; the lint rule could only refuse it, which is why it had accumulated seven `ignore*` options and a bespoke `ignorePattern`. `eslint-config-prettier` was already a devDependency and had simply never been added to the config, so nothing was turning off the rules that fight the formatter. Verified the substantive rules (`no-console`, `no-unused-vars`, `@typescript-eslint/*`) still fire. | AI + tomasmbrito |
| 2026-08-21 | **The order deadline applies to every stock type, not only `on_demand`** (#174) | Keep the `v_stock_type = 'on_demand'` guard, treating the deadline as advisory for limited stock | The argument for the old behaviour is "limited stock is already bounded by stock". It does not hold: stock is replenishable, while `order_deadline` is a separate promise about *when the núcleo places the production order*. The field is set per product in the product form and shown to students, so a limited-stock sweat advertising "encomenda até 20/08" that accepts an order on 21/08 is a commitment somebody has to honour or refund. `p_stock_override` still bypasses it, so POS sales at a stand are unaffected — the check exists to stop students ordering after the run is placed, not to stop the núcleo selling stock already in a box. | AI + tomasmbrito |
| 2026-08-21 | **`Public` on a Notion event fails closed** (#127) | Keep `?? true`, treating an absent property as public | A Notion checkbox is present on every page once the property exists, so the default is only reached when the *property itself* is missing — i.e. someone renamed or deleted it. `?? true` meant that at that moment every event in the workspace silently became public, internal meetings included. Failing closed turns that mistake into an empty public calendar plus a loud log line: visible and recoverable, rather than a silent disclosure. | AI + tomasmbrito |
| 2026-08-21 | **Internal events are read from Notion and cached, not persisted** (#127) | Add a `public` column to `neiist.activities` and let the sync store internal events too | #127 explicitly forbids new tables or schema changes, and for good reason: this view exists to *validate* the Phase 1 model against real records before any table is designed around it. Persisting internal events would commit to a shape before that validation, and would put internal meetings in a table a public page reads — the exact boundary the sync currently keeps clean by deleting them. Caching (5 min) satisfies the issue's requirement not to add an uncached third-party call to a page render. This module is expected to be deleted in Phase 1 (#129), when the website becomes the source of truth. | AI + tomasmbrito |
| 2026-08-22 | **"Board access" is not a hardcoded list of roles — it stays per-role data in `valid_department_roles`, editable by the President/VP** (#185) | (a) make every Direção role `admin`; (b) add a `board` access level distinct from `admin` | Tomás's answer corrected the premise of both options. Direção is not uniform: the **Diretor da SINFO** heads a *secção autónoma* and is "like a different part of NEIIST"; the **Tesoureiro** "is treated like he isn't even a member, he just has the role". Both are correctly `member` in the seed data today — so the "the treasurer would be locked out" framing was **wrong**: that is the intended state, not a defect. Meanwhile a Marketing director is about to be added who probably *should* have board-level access. A hardcoded list would be wrong within the month. The existing model already expresses this exactly — access is a property of the (department, role) pair — and #158 added `update_valid_department_role` plus a PATCH route so it can be changed without a deploy. What remains is the UI half of #158, so the President/VP can do it without a developer. | AI + tomasmbrito |
| 2026-08-22 | **Organisation-wide `admin` is Direção (Presidente, Vice-Presidente, Vogal) plus the Dev-Team Coordenador. The Mesa da Assembleia Geral is not** (#189) | (a) demote both the MAG president and the Dev-Team coordinator; (b) leave both, and accept that team scoping does not hold; (c) invent a `board` access level | Answered by Tomás, and the two halves went opposite ways, which is why (a) and (b) were both wrong. **Dev-Team Coordenador keeps `admin`** — "can still have access to everything for now (just the coordinator, not the other members)" — and that qualifier is load-bearing: the team's other roles are `member`/`shop_manager`, so this is one person, not every developer. **MAG Presidente drops to `coordinator`** — "Mesa da Assembleia Geral should only have access to what we give them access", while "the president and vice president should both have access to everything" refers to Direção. `coordinator` gives the MAG president full power inside the MAG and none outside it, level with their own vice-president who was already `coordinator`. (c) was rejected again for the #185 reason: a second fixed level is still a fixed list. Guarded by `seededAdminRoles.test.ts`, which pins the intended set against `init.sql` so a future `'admin'` seed must be added to the list in the same commit. | AI + tomasmbrito |
| 2026-08-23 | **`app/layout.tsx` re-throws Next's framework signals (option 1 of #153), and the predicate moves to one shared place** | (b) keep the catch and move the session read out of the root layout, preserving static rendering; (c) leave it | Chosen after **measuring**, which is what settled it: the issue framed this as trading correctness for static rendering, and the trade turned out to be free. Before: 21 build lines reading "Failed to resolve the initial user … couldn't be rendered statically", 1 static route. After: **0 such lines, still 1 static route.** `/sitemap.xml` is the only prerendered route and it is a route handler outside this layout, so it never depended on the layout lying. Option (b) was therefore a real refactor buying nothing, and (c) leaves the root layout — which runs on *every* route — telling Next the wrong thing about dynamism. `isFrameworkSignal` also moved to `src/lib/errors/frameworkSignal.ts`: it existed twice, and #111 fixing one copy while `layout.tsx` kept the other is exactly how #153 came to exist. | AI + tomasmbrito |
| 2026-08-25 | **Recruitment: applications kept 6 months after rejection; onboarding does NOT create membership; per-team decisions and WhatsApp links belong to each team's coordinators** (#134) | (a) 12-month or indefinite retention; (b) onboarding auto-creates the membership; (c) board-only review | Four decisions taken together, and the second is the load-bearing one. **Onboarding stays manual**: `add_team_member` remains the single path by which a membership comes into existence. A self-service page reachable by a *non-member* that creates authority is exactly the shape of #193, and the convenience is one click a few times a year. **6 months** is long enough to answer "why was I rejected" and to re-read applications next round, short enough that NEIIST is not holding a growing database of personal data belonging to people with no relationship to it — the GDPR exposure in Notion is a stated motivation for the whole migration (#126), so importing that problem would be self-defeating. **Coordinators decide per team** because they rotate their own WhatsApp links and know who they want; `_ADMIN` is organisation-wide, so the board retains everything without being a bottleneck. | AI + tomasmbrito |
| 2026-08-25 | **A recruitment decision needs two signatures, and a *rejection* needs both too — not just the team** (#217) | (a) the issue's own assumption: a rejection is the team's alone, since nobody is being told they are in; (b) require both only for acceptance and let a single rejection close it | Tomás's wording decided it: "in order for the emails **(of rejection or acceptance)** to be sent, both the coordinator of that team and at least one member of the board should accept". A rejection email is still an email sent in NEIIST's name to a person who applied, and the second pair of eyes is worth as much there as on an acceptance — arguably more, since a rejection is the one nobody revisits. The cost is one extra click on the decisions that were going to be no anyway; the benefit is that no single coordinator can quietly close the door on a candidate. |AI + tomasmbrito |
| 2026-08-25 | **"The board", for the second signature, is `department_type <> 'team' AND access = 'admin'` — derived from data, not a name list** (#217) | (a) hardcode `'Direção'`; (b) check `access = 'admin'` alone; (c) add a `board` flag column | (a) is the thing #185 already decided against, and it would go stale the month a new admin body appears. (b) is actively unsafe and was proved so by mutation: `Dev-Team / Coordenador` is graded `admin` **on purpose** (#189), so checking only the grade makes one team's coordinator the *board* signatory for every other team — #180 all over again, and the test for it fails when `department_type` is removed. (c) is a fixed list wearing a column's clothes. Against the real seed the chosen rule selects exactly Direção's Presidente, Vice-Presidente and Vogal; Conselho Fiscal and Mesa da Assembleia Geral top out at `coordinator`, which is what "Mesa only has what we give them" means in practice. **Consequence to confirm with Tomás:** the Diretores de Atividades are `coordinator`, so they cannot give the board signature today. Changing that is one row in `valid_department_roles`. | AI + tomasmbrito |
| 2026-08-25 | **An event's visibility is four levels on the event, and teams can be added as collaborators — the owning team does not change** (#219) | (a) move the event to whichever team is now involved; (b) give the helping team access to the whole owning team's workspace; (c) keep the `is_public` boolean and add a members-only flag | Tomás described how events actually run: one starts in **Organização de Eventos**, or with the Direção for the bigger ones, and then *grows* — a poster brings in Visuais, a story brings in Divulgação. (a) loses the owner; (b) hands over every other event and meeting that team has, to solve one poster. The `members` level did not exist at all and is the one the workspace most needed: núcleo-wide announcements that are not for the open web. `is_public` stays for now, synced both ways by a trigger, because the Google Calendar sync reads the boolean and #202 was that sync leaking internal meetings to a **world-readable** calendar — the two drifting apart is the failure mode, and a mutation proved the tests did not catch it until an INSERT-path test was added. | AI + tomasmbrito |
