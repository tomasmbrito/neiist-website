# Decision Log

Technical decisions made during NEIIST Website development. Each entry records
the decision, alternatives considered, and rationale.

| Date | Decision | Alternatives | Rationale | Author |
|------|----------|-------------|-----------|--------|
| 2026-07-24 | Use Vitest for testing | Jest | Vitest is faster, ESM-native, better Next.js support | AI + tomasmbrito |
| 2026-07-24 | Keep raw pg (no ORM) | Drizzle, Prisma | Existing codebase uses raw pg extensively; migration risk too high for now | tomasmbrito |
| 2026-08-11 | Yarn is the authoritative package manager; delete `package-lock.json` | Migrate to pnpm (matching upstream), keep both lockfiles | All `package.json` scripts and the husky hooks already assume yarn. Two committed lockfiles can disagree and produce different dependency trees for different developers. pnpm is deliberately deferred, not rejected — it is a breaking change to scripts, CI and the server deploy scripts, and should be its own project. | tomasmbrito |
| 2026-08-11 | Deliver via branch + PR on the fork; human reviews and merges | Full autonomy including self-merge | The code handles real card payments and student PII. For security and payment changes a wrong fix is worse than a slow one, so a human reads the diff before it lands. | tomasmbrito |
| 2026-08-12 | **Identity model is `istid`.** Delete `src/lib/db/repositories/*` and `docker/migrations/001_user_uuid.sql`; adopt the upstream `src/utils/db/*` split instead of reviving the fork's own (#82) | Commit to UUID and mount the migration; keep both halves indefinitely | `neiist-dev` kept `istid VARCHAR(10) PRIMARY KEY`, has since built a whole voting system on `istid` foreign keys, and already shipped the dbUtils split this fork was attempting (28 `istid` / 0 `uuid` references in a query layer that runs in production). The fork's half was 1,025 lines with **zero call sites** that had never executed, targeting a migration `docker-compose.yml` never applied. Choosing UUID would have meant rewriting the existing 60+ SQL functions *and* everything upstream has added since, and diverging permanently on schema — the one thing that makes future syncs impossible rather than merely tedious. External users get a synthetic `istid` in the existing column rather than a UUID primary key. | AI + tomasmbrito |
| 2026-08-12 | Stay on yarn until the upstream sync (#90) completes, then revisit pnpm (#112) | Migrate to pnpm now, matching upstream | The lockfile is the least valuable thing to take from upstream; the valuable parts (security bumps, the dbUtils split, voting) need no pnpm. Changing package manager mid-sync adds an install-layer variable to a merge already touching 145 files, and the deploy scripts are the risky surface. commitlint and release-please are separable from that commit and cheap to adopt alone. | AI + tomasmbrito |
| 2026-08-12 | Sync from `neiist-dev` by cherry-picking per theme in waves, never by merging | `git merge upstream/main`; rebase the fork onto upstream | A merge produces 42 conflicted files simultaneously, most of them API routes carrying the #96–#106 security fixes — the failure mode is a security fix silently reverted. Their version is also not automatically better: their Notion webhook fails open when `VERIFICATION_TOKEN` is unset, which #96 already fixed here. Per-file adoption is the only way to keep what the fork does better. See `upstream-sync-plan.md`. | AI + tomasmbrito |
| 2026-08-12 | **Build a migration runner rather than applying DDL by hand.** `scripts/migrate.mts` + `docker/migrations/` + `neiist.schema_migrations`, wired into both deploy scripts (#148) | A documented manual `psql` procedure; adopting a migration tool (Flyway, node-pg-migrate, Drizzle Kit) | The order-integrity plan asked "who applies DDL to production?" and the answer was *nobody, ever* — no `psql` step existed in either deploy script, in this fork or upstream, across 53 edits to `schema.sql`. A manual procedure would have kept the schema dependent on someone remembering; Tomás explicitly asked not to do it by hand. A dependency was rejected because the requirement is small (ordered SQL files, a ledger, a lock) and the repo's constraints are unusual — plpgsql dollar-quoting means the runner must *not* split on `;`, and blue/green deploys mean it must hold a lock. ~250 lines of `pg`, which is already a dependency, beats a tool whose defaults fight both constraints. | AI + tomasmbrito |
| 2026-08-12 | **Every migration must be idempotent**, and `docker/schema.sql` must be edited alongside it | Ordinary forward-only migrations that assume a known starting state; generating `schema.sql` from the migrations | Production's schema is unmeasured and unreconstructable (§1 of `database-migrations.md`), so a migration cannot assume what it is starting from. Idempotence is what makes the runner safe to point at it anyway. Keeping `schema.sql` as the hand-maintained end state means fresh environments never replay history — at the cost of writing the change twice, which is the deliberate trade. | AI + tomasmbrito |
| 2026-08-12 | **Tests run against a real Postgres, not mocks** (#52) | Mock `pg`; use `pg-mem` | The first tests cover `withTransaction`, whose entire contract *is* Postgres behaviour — that `COMMIT` on an aborted transaction returns the tag `ROLLBACK` and raises nothing, that a pooled connection is a different transaction. A mock would assert only that we still believe what we already believed, and the aborted-`COMMIT` bug is precisely a case where the belief was wrong. CI gets a service container; the job is kept separate from `quality` so the build keeps proving it needs no database (#106/#109). | AI + tomasmbrito |
| 2026-08-12 | **`/shop` keeps `force-dynamic`; the other three pages drop it** (#111) | Remove all four, now that the dynamic signal propagates; keep all four | Measured, not argued: with all four removed the build fails on `/shop` with no database reachable, reintroducing the build-time database dependency #106/#109 removed. `/shop` is the only one of the four that never touches the session, so its only dynamism is a database read — which Next does not treat as a signal. The other three call `serverCheckRoles`/`requireRoles` first, and that `cookies()` read is now itself the signal. | AI + tomasmbrito |
